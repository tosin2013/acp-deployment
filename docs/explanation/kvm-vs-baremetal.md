# Understanding KVM vs bare-metal deployment paths

`acp-deployment` supports two fundamentally different infrastructure paths for getting OpenShift nodes running: virtual machines on a KVM hypervisor (the IBM Cloud path) and direct installation on physical servers (the bare-metal path). While both paths produce the same OpenShift cluster and support the same cluster topologies (Converged HA and SNO), they differ significantly in how nodes are created, how DNS works, and critically, how ODF storage networking is configured.

> **Short answer:** Use KVM to develop and test. Use bare-metal to deploy. Both support Converged (3-node) and SNO for edge sites.

---

## Why two paths exist

The ACP reference architecture serves two distinct audiences:

**IBM Cloud KVM** is the path for teams developing and validating ACP automation. You get a full cluster in hours, you can tear it down and rebuild it to test changes, and the environment is reproducible. This is how `acp-deployment` itself is developed and tested. All of the v4.21.0 validation was done on this path.

**Bare-metal direct** is the path for production ACP deployments at edge facilities. Physical servers at industrial sites are real hardware — they have different NICs, different BMC firmware, different switch configurations. This path is what the project ultimately exists to enable. Because every site is different, community contributions for specific hardware configurations are a core part of the bare-metal story.

The two paths share the same OpenShift cluster topology, the same post-install playbooks, and the same application surface. The differences are purely in the infrastructure layer beneath OpenShift.

---

## Cluster topologies: both paths, same choice

Both KVM and bare-metal support two cluster topologies relevant to edge ACP deployments:

### Converged (3-node compact HA)
Three servers run both control-plane and workloads. ODF provides block, file, and object storage from local disks. AAP, Pipelines, and OpenShift Virtualization all run on the cluster.

Best for: ACP sites with 3 servers and full platform services (DCN management, pipelines, VM workloads).

### SNO (Single-Node OpenShift)
One server runs everything. No ODF (Ceph requires 3 nodes for quorum). Storage is provided externally or via a simple storage class (NFS, iSCSI, hostPath).

Best for: Space-constrained or power-constrained edge sites, remote locations with a single server budget, or development environments where you want a minimal footprint.

> **SNO on KVM** is useful for iterating quickly on playbooks that target SNO deployments before committing to physical hardware.

## Node creation

**KVM:** `hack/deploy-kvm-vms.sh` calls `virt-install` to create VMs with pre-generated MAC addresses. The installer ISO is attached as a virtual CDROM. The Agent-Based Installer detects that it is inside a VM and proceeds with RHCOS installation to the virtual disk. When installation completes, the installer shuts down the VM (does not reboot). `hack/watch-and-reboot-kvm-vms.sh` detects the shutdown and reboots the VM into the installed OS.

**Bare-metal:** `hack/deploy-on-baremetal.sh` uses the Redfish API on each server's BMC to mount the ISO as virtual media and set a one-time boot from CD-ROM. Physical servers reboot themselves after RHCOS installation — no watcher script is needed. The Redfish path requires iDRAC 9+, iLO 5+, or an equivalent BMC with virtual media support.

---

## MAC addresses

**KVM:** MAC addresses are synthetic — generated by `hack/generate-kvm-macs.sh` using the `52:54:00:` QEMU prefix. They are written into `extra-vars.yml` before ISO generation, so the ISO and the VMs are always consistent.

**Bare-metal:** MAC addresses are read from hardware labels, BIOS/BMC web UI, or tools like `ipmitool`. They must be manually entered into `extra-vars.yml`.

---

## DNS architecture

**KVM:** The IBM Cloud bare-metal server has a single public IP. External DNS (Route53) maps `api.*` and `*.apps.*` to that IP. HAProxy forwards external traffic to the VIPs inside the KVM private network. Internal DNS (dnsmasq on `virbr-1925`) resolves cluster node hostnames within the VLAN. The VyOS router provides routing between VLANs and the internet.

**Bare-metal:** DNS is handled by BIND running in a Podman container on the helper node (`external_dns: false`). The helper runs BIND on the machine network, serving forward and reverse records for all cluster nodes. No HAProxy is needed if the helper has a public IP or if external access is handled separately.

## The most important difference: ODF network isolation

The most consequential difference between the two paths is how ODF storage networking works — and this difference has caused real failures.

**Bare-metal with `odf_use_multus: true`:**
Physical servers have multiple NIC bonds (`bond0` for cluster traffic, `bond1` for storage). Ceph replication traffic can be isolated to `bond1` using Multus — a CNI plugin that attaches an additional network interface (via macvlan) directly to a pod. This prevents Ceph's replication I/O from competing with workload and API traffic on `bond0`. For production deployments where storage throughput matters, this isolation is important.

**KVM with `odf_use_multus: false`:**
KVM uses virtio virtual NICs (`eth0`, `eth1`, `eth2`). The virtio driver does not support macvlan subinterfaces — the kernel rejects the ioctl call that would create one. Attempting to use Multus macvlan on KVM causes ODF pods to fail with `error adding container to network "ocs-public-cluster": Link not found` and the StorageCluster to stay stuck in `Progressing`.

The fix is `odf_use_multus: false`, which instructs the deployment to skip NAD creation and configure the StorageCluster without a storage network attachment. ODF storage traffic shares the primary `eth0` interface. For a testbed this is acceptable; for production on physical hardware, Multus isolation is strongly preferred.

This distinction is now enforced by a preflight check in `hack/verify-odf-prerequisites.sh` that fails fast if KVM is detected with `odf_use_multus: true`.

For the full reasoning, see [ADR-0005](../adrs/adr-0005-odf-on-local-nvme-with-multus-storage-network.md) and [Understanding ODF storage design](./odf-storage-design.md).

## When to choose which path

| Scenario | Recommended path |
|----------|-----------------|
| Learning ACP deployment for the first time | 🖥️ KVM on IBM Cloud |
| Developing or testing new Ansible roles/playbooks | 🖥️ KVM on IBM Cloud |
| CI/CD validation of deployment changes | 🖥️ KVM on IBM Cloud |
| Performance benchmarking for ODF | 🔩 Bare-metal direct |
| Production ACP deployment at an industrial facility | 🔩 Bare-metal direct |
| Edge SNO deployment at a space-constrained site | 🔩 Bare-metal direct (SNO) |
| Sites with existing Redfish-capable servers | 🔩 Bare-metal direct |
| Need to recreate/destroy the environment quickly | 🖥️ KVM on IBM Cloud |

## Contributing bare-metal configurations

Because bare-metal hardware varies so much between sites, the bare-metal path improves through community contributions. If you deploy on:

- A specific server vendor (Dell, HPE, Supermicro, Lenovo, Cisco UCS)
- A non-Route53 DNS provider (Cloudflare, corporate DNS, split-horizon)
- An unusual NIC configuration (SR-IOV, single NIC, mixed bonding modes)
- An air-gapped or restricted network environment

...please share your working `extra-vars.yml` and `nodes.yml` (with credentials removed) as a new example directory. See [CONTRIBUTING.md](../../CONTRIBUTING.md) for how.

---

## What is the same in both paths

Once OpenShift is installed, both paths are identical:
- The same `site-post-install.yml` playbook runs
- The same OLM-based operator installation pattern applies
- The same ZeroSSL TLS configuration works
- The same `KUBECONFIG` and `oc` CLI work identically
- ADRs 0001–0013 apply to both paths equally

The differences are entirely in the infrastructure provisioning layer, not in OpenShift itself.
