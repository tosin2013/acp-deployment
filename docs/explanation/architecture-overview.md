# Architecture overview: how ACP deployment is structured

`acp-deployment` is a layered system. Understanding the layers and how they relate to each other helps you know where to look when something breaks and where to make changes when extending the system.

---

## The four layers

```
┌─────────────────────────────────────────────────────────────┐
│  Platform Services (ODF, Pipelines, AAP, Virt, cert-manager) │  ← Layer 4
├─────────────────────────────────────────────────────────────┤
│  OpenShift Container Platform 4.21                           │  ← Layer 3
├─────────────────────────────────────────────────────────────┤
│  Compute nodes (KVM VMs or physical servers)                 │  ← Layer 2
├─────────────────────────────────────────────────────────────┤
│  Infrastructure (DNS, networking, TLS, storage disks)        │  ← Layer 1
└─────────────────────────────────────────────────────────────┘
```

Each layer is provisioned from the layer below it. `acp-deployment` automates all four layers, starting from Layer 1 and finishing with Layer 4.

---

## Layer 1: Infrastructure

Infrastructure in `acp-deployment` means:

**DNS:** Two systems handle DNS. External DNS (Route53) maps the public hostnames (`api.*`, `*.apps.*`) to the server's public IP. Internal DNS (dnsmasq on the KVM VLAN bridge, or BIND-in-Podman for bare-metal) resolves cluster node hostnames within the private network. Both must be correct before any node boots.

**Networking:**
- On KVM: VLAN networks (`virbr-1924/1925/1926`) are created by libvirt. A VyOS router VM provides layer-3 routing between VLANs and the internet. HAProxy on the bare-metal host provides external load balancing.
- On bare-metal: The physical network switch provides VLANs and routing. The helper node runs HAProxy and BIND.

**Storage disks:** On KVM, virtual disks (`vdb`, `vdc`) are created by `virt-install`. On bare-metal, physical NVMe drives are pre-existing. LSO discovers and provisions PVs from these disks for ODF.

**TLS:** cert-manager issues ZeroSSL certificates via DNS-01 ACME challenge against Route53. Certificates are stored as Kubernetes Secrets and referenced by the `IngressController` and `APIServer` resources.

---

## Layer 2: Compute nodes

In the KVM path, compute nodes are libvirt VMs: 16 vCPUs, 48 GiB RAM, 3 virtual disks (`vda` OS, `vdb`/`vdc` ODF). They are connected to three virtual networks (VLAN 1925 for cluster traffic, 1924 for management, `acp-storage` for ODF when using Multus).

In the bare-metal path, compute nodes are physical servers connected to bonded NICs: `bond0` for cluster traffic and `bond1` for ODF storage.

Both types are bootstrapped from an Agent-Based Installer ISO. The ISO is generated by `openshift-install` and contains all node configuration (nmstate interface config, static IPs, MAC addresses). No DHCP or PXE infrastructure is needed.

---

## Layer 3: OpenShift

OpenShift 4.21 installs via the Agent-Based Installer. The ACP reference architecture uses a **3-node compact** (converged) topology: all three nodes run both control-plane and worker roles. This maximises hardware utilisation in environments with exactly 3 servers.

The Single-Node OpenShift (SNO) topology is also supported (`architecture: non-ha`). SNO runs everything on one node but does not support ODF (Ceph requires 3 nodes for quorum).

OVN-Kubernetes is the CNI (Container Network Interface) plugin. NMState handles static network configuration and bonding. Multus provides secondary network attachment for ODF storage pods (bare-metal only).

---

## Layer 4: Platform services

Five platform services are deployed via the OLM pattern (ADR-0006):

**ODF (Ceph+NooBaa):** Block, file, and object storage. Deployed first because all other services with persistent storage depend on it.

**cert-manager + ZeroSSL:** Automates TLS certificate issuance and renewal. Deployed second so that all operator routes get trusted certificates before users see them.

**OpenShift Pipelines (Tekton):** CI/CD pipeline engine. Deployed third — no storage dependency.

**Ansible Automation Platform:** The DCN management layer. Deployed fourth because it needs ODF PVCs for its PostgreSQL database.

**OpenShift Virtualization (KubeVirt):** VM workload support. Deployed fifth — optional, requires nested virtualisation on KVM hosts.

## The helper node: the deployment control plane

Every Ansible playbook in this project targets a single `[helper]` host. In the IBM Cloud path, the helper is the bare-metal server itself (running Ansible against `localhost`). In the bare-metal path, the helper is a separate server on the same network as the cluster.

The helper is where:
- `openshift-install` runs to generate the agent ISO
- The ISO is served over HTTP (`/var/www/html/`)
- HAProxy and dnsmasq run (IBM Cloud path)
- All `redhat.openshift.k8s` calls execute (against the cluster API via kubeconfig)
- All deployment artifacts are stored (`~/cluster_<name>/install/`)

This concentration of functions on a single node simplifies the operational model (one machine to manage, one kubeconfig, one set of credentials) at the cost of a single point of failure during deployment. See [ADR-0003](../adrs/adr-0003-helper-node-centric-deployment-model.md) for the full rationale.

## Key interfaces

**`examples/*/extra-vars.yml`:** The single source of truth for cluster configuration. All playbooks and scripts read from this file. See [Reference: extra-vars.yml](../reference/extra-vars.md).

**`hack/env.sh`:** Shell environment variables (`CLUSTER_NAME`, `BASE_DOMAIN`, `EXTERNAL_IP`, `HOSTED_ZONE_ID`). Must be sourced before any `hack/` script.

**`KUBECONFIG`:** After installation, all post-install operations use the cluster kubeconfig at `~/cluster_<name>/install/auth/kubeconfig`.

**`playbooks/collections/requirements.yml`:** Ansible collection dependencies. Install with `ansible-galaxy collection install -r playbooks/collections/requirements.yml`.
